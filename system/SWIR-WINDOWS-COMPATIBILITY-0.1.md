# SWIR OS System Edition — Windows Compatibility Service 0.1

## Scope

This milestone adds the first executable, fail-closed prototype of the System Edition `windows-compat` path. It is a user-space compatibility broker for Windows applications and does not pretend that Windows programs or Windows kernel drivers execute natively on Linux.

The prototype is deliberately narrower than the final service. It establishes the security and lifecycle boundaries that later Wine/Proton packaging, Store integration and real hardware testing must preserve.

## Launch flow

```text
signed SWIR provider manifest
        |
        v
trust verification gate
        |
        v
SWIR Compatibility Service
        |
        +--> provider allowlist: swir.compat.wine / swir.compat.proton
        +--> per-application managed prefix
        +--> runtime executable allowlist/root check
        +--> Windows entry point containment check
        +--> sanitized host environment
        +--> service-owned WINEPREFIX / WINEARCH / Proton data path
        |
        v
spawn(runtime, argv[], shell=false)
```

A Wine/Proton runtime is administrator-provisioned or installed later by an authenticated System Package Service. Applications cannot supply an arbitrary runtime executable and cannot turn the launch into a shell command.

## Managed prefix policy

Architecture 0.1 implements only a **per-application managed prefix**. The default service root is:

```text
/var/lib/swir/compat/prefixes/<app-id>/
```

Each prepared prefix contains `.swir-compat.json` binding it to the application ID, provider and Windows architecture. Existing metadata must match before launch. Prefix directories and runtime paths are canonicalized, and symlink/path traversal outside the managed root is rejected.

The package's Windows entry point must resolve inside its own prefix. Direct compatibility launch is limited to `.exe` and `.com` user applications in this prototype; `.sys`, installers and other artifacts are not treated as generic executable application entry points. Windows kernel drivers remain unsupported as a Linux driver path.

## Runtime policy

The service accepts only the reserved providers:

- `swir.compat.wine`
- `swir.compat.proton`

The provider maps to a separately configured absolute runtime executable. The runtime must resolve under an approved runtime root and be an executable regular file. The service constructs argv arrays and always launches with `shell=false`.

Host environment inheritance is allowlisted. Variables such as `LD_PRELOAD`, `NODE_OPTIONS` and caller-supplied `WINEPREFIX` are not inherited. `WINEPREFIX`, `WINEARCH`, and for Proton `STEAM_COMPAT_DATA_PATH`, are generated by the broker from the managed profile.

## Trust requirements

A launch is rejected unless all of these hold:

1. manifest schema is `swir.package-provider/0.2`;
2. target editions include `system`;
3. execution class is exactly `windows-compat`;
4. provider is Wine or Proton from the reserved allowlist;
5. package manifest requires signature verification;
6. the caller provides a completed trust-verification result;
7. prefix policy is `per-app`;
8. prefix metadata, runtime path and Windows entry point pass containment checks.

This service does not perform package installation or signature verification itself. Those responsibilities stay in the common Package/Store trust and transaction layers so compatibility execution cannot silently bypass installation policy.

## Process lifecycle

`WindowsCompatibilityService` tracks one active process per app ID in the initial prototype, exposes `get()` and `list()`, emits start/exit/failure state, and only accepts the bounded stop signals `SIGTERM`, `SIGINT` and `SIGKILL`. Running records cannot be forgotten until they reach a terminal state.

## Verification

The accompanying self-test verifies trust failures, provider/class restrictions, prefix containment, metadata binding, environment filtering, runtime-root enforcement, `.sys` rejection, Wine/Proton argument construction, `shell=false`, process lifecycle and stop-signal policy. A separate contract validator cross-checks this service against the existing package-provider and trusted-source allowlists.

## Roadmap gate

This prototype materially advances the future managed Wine/Proton compatibility service, but **does not make the System Edition roadmap item complete**. The roadmap checkbox must remain open until a maintained Linux base actually provisions approved Wine/Proton runtimes, signed package installation is integrated with the compatibility profile lifecycle, and representative Windows applications pass end-to-end launch, filesystem-permission, update, rollback and recovery tests on the System Edition host.
